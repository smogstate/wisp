# Wisp

AI assistant for World of Warcraft (WoW Forever first): a Python overlay beside the game plus a small Lua addon.

**The wiki is the source of truth.** Read `wiki/Home.md` first; every product
and architecture decision lives there. Update the wiki when decisions change.

## Quick facts

- Two halves: overlay in Python on Windows (chat, LLM, tools, clipboard), addon in Lua (runs pasted commands through other addons).
- Red lines (wiki/Red-Lines.md): never send input to the game, never touch game memory, never run pasted text as Lua. "No account risk, never."
- The player never types `/reload`; chat never involves copy-paste. Paste is only for commands into the game.
- Commands use the extensible `WISP1` protocol; one Lua file per addon integration (wiki/Protocol.md).
- BYOK: Anthropic, Kimi, OpenRouter behind one provider contract modelled on kintale's (wiki/LLM-Providers.md). Tools return validated structures, not pages (wiki/Tools.md).
- No live data out of the game except a screenshot. Do not reintroduce the pixel beacon.
- Code so far is the MVP: `addon/Wisp` (Lua) and `wisp/` (Python, stdlib server + Anthropic SDK + pywebview). Run the tests with `npm install && python3 tests/test_mvp.py`; they need Node for a Lua VM (or `WISP_LUA=/path/to/lua5.1`, which is the game's Lua version), no game and no key. `python -m wisp --fake` shows the interface with a scripted model.
- `Wisp.exe` is a launcher (`wisp_app.py`) that runs Wisp's code from files: the copy inside it, or a newer one in `%APPDATA%\Wisp\code` put there by `wisp/update.py`. An ordinary push updates players through `wisp-code.zip` alone; the exe is replaced only when the *runtime* changes (a fingerprint of `requirements.txt` and `wisp_app.py`). So: a new library, or a stdlib module not listed in `wisp_app._carried`, needs one of those two files touched, or old exes will fail the new code's self-check and stay on the old version. The build tests both paths on Windows.
- Players get `Wisp.exe`, not Python: `.github/workflows/build.yml` builds, tests and publishes it as the `mvp` release on every push that touches code. `--smoke FILE` is the self-test it runs on the built exe. Nothing may require a command line or an environment variable.
- Three providers: Anthropic (its own SDK), Kimi and OpenRouter (the `openai` SDK on the shared OpenAI-shaped wire, `OpenAIChat`; OpenRouter reads limits, prices and abilities per model from its public catalogue). A chat object owns its history in its provider's format; a conversation never changes provider. Tests: `tests/test_anthropic.py`, `tests/test_openai.py`, each against a local stand-in API.
- The model never handles coordinates: locations carry refs, and `waypoint` accepts only refs. Keep that when adding tools.
- The model never adds up quantities or prices either: `wisp/crafting.py` does the sums (`craft_plan`), and `shopping_list` takes the same plan. Recipes are read by the addon while the profession window is open and kept in `WispData`.
- `wisp/assets.py`: investments. Trades as the player reports them, money parsed in code from text with units (never a bare number), every figure derived in code.
- `wisp/gathering.py`: GatherMate2's nodes, zone rankings and routes (built in code, one ref for `waypoint`).
- `wisp/farming.py`: no addon has drop rates for ordinary loot (Questie's are quest items only), so the addon records the player's own looting (`WispData.loot`) and everything about farming is computed from that.
- A daily spending limit (`App.spent_today`, `DAILY_CAP`, default $5) is checked before every question and between requests; anything new that spends the player's key must go through `App.ask`, or hand its usage to `App.add_spend` as Check setup does, so it is counted. What counts is `usage["counted"]`: the real cost where `llm.PRICES` has the model, the dearest known price where it does not (never zero). Add a model's price to `PRICES` when Anthropic lists it.
- `/research` is the only way the web is used: `answer(..., research=True)` raises the round budget, adds Anthropic's server-side web tools with hard `max_uses` caps, and offers `report`, whose sources are checked against the pages actually returned. Keep the caps hard and shown up front.
- `wisp/blizzard.py`: Blizzard's Battle.net API for WoW Forever (undocumented), with the player's own developer client from Settings (credential store entry `battlenet`, "id:secret"). Check setup probes it; `Live` serves the `live_auctions` tool: one house's listings, cached about an hour, the house found by the player's own auctions and remembered in the config (`bnet_house`).
- Every recipe in the game: the addon walks `C_TradeSkillUI.GetRecipeInfoForSkillLineAbility(1..80000)` once per game version in the background (`WispRecipes`), so the graph does not stop at the player's professions. `wisp/tree.py` walks it: `craft_tree` down to raw materials, `item_uses` up to every product; all arithmetic in code. Recipe books of every character are merged (`owner` on a recipe = an alt, by class and level only; `world` = nobody of the player's has it). `craft_tree` takes held stock first (`Crafting.stock()`: bags, bank, the shared bank, then each other character's bags and bank from `snapshot.alts`) and its card carries the Auctionator list for the rest. An alt's name goes on cards only; the model gets class and level.
- One-click cards: `wisp/inbox.py` writes a WISP1 message into 100 load-on-demand slot addons (`Wisp_In001..100`) and raises a silent-sound signal in `Wisp_Inbox`; the addon's inbox section sees the signal, loads the next slot and hands the text to the same `receive()` as a paste. Message numbers are send times in ms (written with `.0`). Files must exist when the game starts; a played sound stays cached for the game process. `/wisp sync` reloads the UI, which saves the snapshot like a logout.
- `App.load_game()` builds the `Game` (snapshot, quest/item/recipe indexes, the graph) once and keeps it; it is built again only when the game's saved file changes (path, mtime, size) or Wisp's language does. So a `Game` now lives across questions: per-answer state must be reset where it is used (`game.cards` is, in `answer()`).
- **The graph never goes into the model's context** (Denis, 2026-11-12): it lives in Wisp's memory and is reached only through tools, each of which hands back a bounded slice (a count of what was left out, never the rest). `test_graph_stays_out_of_context` holds every graph tool's answer under a size on a full-size, tangled game. Keep new tools the same: cap lists, say how many were left out.
- `wisp/questdb.py`: Questie's whole quest list, read once by the addon in the background after login (a coroutine, a slice per frame) and kept in its own saved variables `WispQuests`/`WispQuestsKey`; rebuilt only when Questie's version, the locale or the character changes. Whether a quest is open is decided in code.
- `wisp/graph.py` is the item graph: items tie recipes, quests, bosses, vendors, drops and prices together, and `item_links` returns one step around an item. New data that mentions items should join it. Questie's whole item list (`WispItems`, read by the addon like the quest list) gives sellers and drops for any item; a recipe item is tied to the recipe it teaches by the name after the colon (`recipes` with `search`).
- Auction prices over time live in `wisp/market.py` (SQLite, `%APPDATA%\Wisp\market.sqlite`), fed by the per-day record the addon takes from Auctionator at logout. Rankings, trends and the estimate are computed there; the model only words them.
- Language: everything Wisp writes itself is in the player's language (the game client's locale, unless Settings says otherwise). English text is the key: `t()`/`tn()` in `wisp/i18n.py` for Python, `T()`/`TN()` and the `RU` table in `ui.html` (the markup's fixed texts are translated by `localize()`), `L()` in the addon. A new user-facing text needs its Russian or `test_localization` fails. The model answers in the player's language by itself.
- `evals/`: the assistant's eval. `cases.py` holds the questions (Denis's own, on the test game), each with the tools a right answer needs, the facts it must hold, what it must never say, and a written right answer. `python3 evals/run.py --check` is free and runs inside `tests/test_mvp.py`: every written right answer must still pass through the real tools, and an empty answer must not. `python3 evals/run.py` asks the real model (paid, `ANTHROPIC_API_KEY`, asks before spending) and writes `.claude/hillclimb/answers/`. `--via cli` needs no key: it asks through `claude -p` on the signed-in subscription, with Wisp's prompt and tools served by `run.py --serve` (Claude Code's loop, not `answer()`), and writes `.claude/hillclimb/answers-cli/`; Cases marked `game: ru` run on the same game with its names in Russian (`RU_NAMES`, `run.russian`), asked the way a Russian player writes them. Haiku 5.5 on 2026-11-12, three repetitions: 173 of 174 over 58 cases, tuned on these same cases (no held-out set). A new tool or a changed test game needs its cases kept true; grading is code only, no judge.
- Names as typed: `questdb.best()` is the one matcher for a name the player or the model wrote (items in `graph.find`, prices in `Crafting.find`, recipes in `recipes` with `search`): exact, else the words or their stems (`stems()`: endings cut, so «тонкую нить» is «Тонкая нить»), names of the query's own length first. The prompt tells the model to search in the player's own words and never translate a name. Every lookup of a typed name goes through it (`pick()` = the exact name alone, else candidates): items, prices, price history, recipes, zones, gathering nodes, dungeons, professions. Never match a name in SQL: SQLite's `lower()` and `LIKE` know Latin letters only. A name not found answers with `Game._as_written()`, which says outright when the game is Russian and the name asked for is not.
- `checks/` is throwaway code for milestone 0 (wiki/Checks.md), not part of the product.
- Does not use Loom.
